# Архитектура HexTactics

Документ описывает модули, зависимости, структуру папок, модель данных и план
этапов. Конкретные правила и формулы — в [DECISIONS.md](DECISIONS.md),
формат файлов — в [DATA_FORMAT.md](DATA_FORMAT.md), ход работ — в
[STAGES.md](STAGES.md).

## 1. Стек

| Что | Выбор | Почему |
|---|---|---|
| Язык | C# 12 / .NET 8 | Производительность, строгая типизация, тот же язык в ядре и UI |
| Движок | Godot 4.4.1 .NET (Forward+) | Бесплатный, хороший UI-тулкит, 3D, экспорт под Windows x64 |
| Данные | JSON (`System.Text.Json`), версия формата в каждом файле | Читаемо, легко мигрировать, без зависимостей |
| Тесты | xUnit | Стандарт для .NET, запускаются без Godot |

Многопоточность не используется: симуляция однопоточная и детерминированная.

## 2. Ключевой принцип: ядро отдельно от визуализации

```
┌──────────────────────────── game/ (Godot) ───────────────────────────┐
│  App (меню, режимы)   Render (доска, юниты, оверлеи, камера)         │
│  Battle HUD (панели, меню действий, очередь, журнал)                 │
│  Editor (карты, юниты, навыки, эффекты, состояния, правила, ...)     │
│            │ команды (ICommand)            ▲ чтение состояния/событий │
└────────────┼───────────────────────────────┼─────────────────────────┘
             ▼                               │
┌──────────────────────── src/HexTactics.Core (чистый C#) ─────────────┐
│ Hex    — координаты, направления, линии, кольца, повороты            │
│ Content— определения (Def), БД контента, JSON, валидация, миграции   │
│ Sim    — Simulation: фиксированный тик, RNG, события, журнал         │
│   Map, Units/Stats, Movement/Pathfinding, Commands, Ap,              │
│   Combat, Skills/Areas, CellEffects/Synergies, Statuses, Vision,     │
│   AI, Scenario                                                       │
│ Expr   — безопасный парсер формул (белый список)                     │
└──────────────────────────────────────────────────────────────────────┘
```

* Ядро **не ссылается на Godot**. Его можно запускать в тестах, в
  консольном стресс-тесте и в будущем — на сервере.
* UI не меняет характеристики юнитов напрямую. Всё, что делает игрок, —
  это команды (`Simulation.Submit(...)`), проходящие те же проверки, что и
  команды ИИ.
* Боевая логика одна для всех фракций: союзник, враг и нейтрал — это
  просто значение `FactionId` и отношения фракций.
* Рендер читает состояние симуляции и события; порядок отрисовки не
  влияет на результат (RNG принадлежит симуляции).

## 5. Порядок тика симуляции

Один тик = `1 / TicksPerSecond` секунды симуляционного времени (по умолчанию
20 тиков/с = 50 мс). Подсистемы вызываются строго в этом порядке, юниты —
по возрастанию `Unit.Id`:

1. Сценарий: таймеры, волны, триггеры.
2. ИИ: юниты, у которых истёк интервал решения, формируют команды.
3. Юниты: восстановление ОД и ресурсов, перезарядки, тики состояний.
4. Команды: продвижение текущего действия каждого юнита (шаг, поворот,
   подготовка навыка, восстановление, ожидание).
5. Отложенные этапы навыков.
6. Эффекты клеток: тики, истечение, распространение, синергии.
7. Обработка очереди реакций (с лимитом глубины и числа событий).
8. Видимость (по интервалу), смерть/очистка, проверка победы/поражения.

## 6. Модель данных (кратко)

Контент (определения, редактируются в редакторе) отделён от состояния боя:

* **Определения** (`*Def`): `TerrainDef`, `StatDef`, `ResourceDef`,
  `DamageTypeDef`, `FactionDef`, `UnitDef`, `SkillDef` (+`AreaDef`,
  `SkillStageDef`, `SkillEffectDef`), `PassiveDef`, `CellEffectDef`,
  `SynergyDef`, `StatusDef`, `AiProfileDef`, `RulesDef`, `MapDef`,
  `ScenarioDef`. Все имеют `Id`, `Name`, `Description`, `Tags`.
* **Состояние боя**: `Simulation` → `BattleMap` (клетки с эффектами и
  занятостью), `Unit` (HP, ОД, ресурсы, состояния, очередь, текущее
  действие, направление), активные касты, RNG, журнал.

Подробности полей — в коде (`src/HexTactics.Core/Content/Defs`) и
[DATA_FORMAT.md](DATA_FORMAT.md).

## 7. Godot-слой

* **Render**: доска строится одним `ArrayMesh` (гексагональные призмы с
  фаской, высота уровнями), объекты местности (стены, камни, деревья,
  ящики) — простые низкополигональные формы. Камера — «стол» с наклоном
  60° (настраивается), панорамирование, зум, поворот шагами по 60°.
  Выбор гекса — пересечение луча с плоскостями высот (без физики).
* **Battle**: драйвер симуляции (аккумулятор времени × скорость →
  фиксированные тики), ввод → команды, HUD.
* **Editor**: общий `PropertyGrid` строит формы по атрибутам `Def`-классов
  (подписи, подсказки, диапазоны, ссылки на другие сущности, условная
  видимость полей). Поверх него — специализированные редакторы карт,
  навыков (маска на гекс-поле), синергий (таблица), сценариев.
* Клики по UI не попадают в карту: мир обрабатывает только
  `_UnhandledInput`.

## 9. Часть 2: расширение

Решения — в [DECISIONS_2.md](DECISIONS_2.md). Новое встраивается в ту же
схему: определения (данные) → симуляция (ядро без Godot) → рендер/UI.

### 9.1 Новые категории контента

| Категория | Файл | Назначение |
|---|---|---|
| `MapTemplate` | `map_templates/<id>.json` | шаблоны карт (10 × 8 и др.) |
| `Layer` | `layers.json` | слои положения: наземный, воздушный, подземный, свои |

закреплены на версии (`id@N`).

### 9.3 Порядок тика (дополнение)

Сценарий (цели, волны, маркеры) → ИИ → **автоатаки** → юниты/состояния
→ **блокирование** → команды (движение учитывает блок и слои; вход в
яму → падение) → отложенные этапы навыков → эффекты клеток (вход,
нахождение, соседство, выход) → реакции → видимость и **знания** →
очистка → проверка целей.
